# 仓库、启动与文档维护

用于仓库操作、运行环境、提交或文档维护；业务/样式任务无需每次加载。

## 仓库边界

项目根目录统一管理代码、当前业务文档、历史来源及必要验证证据。`frontend/`不是子模块。初始化前其Git为空，无提交/远程/跟踪文件；旧元数据和图谱备份在`.local-backups/repo-init-20260921/`，不入库。恢复备份只用于诊断，不能在当前根仓库内重新造成嵌套仓库。

纳入：源码、package-lock、mock-only环境预设、测试、规范、许可证、历史展开文档、合成数据测试证据。排除：node_modules、dist、图谱数据库、运行临时目录、密钥、本机备份、重复ZIP交付包。证据目录可保留有意义的日志；实际凭证或真实资料不因位于evidence就允许提交。

提交前检查工作区与暂存清单；仅提交授权内容。初始提交包含现有项目基线，之后按任务切片。提交、远程推送和发布分别按授权执行；当前部署事实见[公网部署记录](../implementation/public-deployment.md)。

## 分支与发布

用户于2026-09-21确认：主分支名为`release`，所有其他分支都是功能分支，最终以主分支发布。

- `release`是GitHub默认分支、唯一长期主分支及发布来源；不再维护`main`、`master`或长期`develop`分支。
- 每项功能、修复、文档或重构都从最新`origin/release`建立短期`feat/<主题>`分支。开始前检查工作区，保护未提交改动；不要在`release`上直接开展日常开发。
- 功能分支完成相应检查后提交PR，目标分支选择`release`；合并后删除已合并的功能分支，不保留与发布分支并行的长期开发线。
- 发布使用`release`上已验证的明确提交；如需版本标记，在该提交上创建发布标签。功能分支不作为正式发布来源。
- 分支合并、推送和部署仍按用户授权分别执行；合入`release`不等于服务器或APK自动更新，本次不新增自动部署流水线。
- 本次首次迁入GitHub，将原本地`main`改名为`release`，已有提交完整保留；仓库约定经本地功能分支验证后快进合入，再首次推送。

远程仓库为[Symplify62/yanxu](https://github.com/Symplify62/yanxu)，保持私有；默认分支`release`，已开启PR合并后自动删除分支。2026-09-21尝试启用强制PR、禁止强推/删除时，GitHub返回403并要求升级Pro或改公开。因此当前PR流程属于协作约定，不能宣称已获得平台硬性分支保护；不为此自动改公开或购买套餐。后续如开通支持的套餐，再按[GitHub分支保护说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)启用。

## 运行与验证入口

依赖/脚本以[package.json](../../frontend/package.json)为准；[前端README](../../frontend/README.md)提供启动步骤。当前默认本地5178端口，`prototype.html`为确认A的入口。先检查端口上的服务归属，再决定复用或启动，不中断其他任务的服务。

fresh clone时在frontend运行npm ci，再运行其build/preview脚本。旧原型的MSW预设为`VITE_MOCKS=true`；真实公共页面从`public.html`单独启动，后端依赖与密钥见[后端说明](../../backend/README.md)。Android构建见[App说明](../../android/README.md)，模型权重和运行数据不随Git克隆。

文档检查从根目录运行：`python3 tools/check_docs.py`。它检查当前导航文档的本地链接、AGENTS长度、前端专题可达性及任务路由样例；不证明业务规格已实现。

代码图谱用于非平凡代码理解/影响分析；新根仓库初次需要时在根目录执行GitNexus索引。索引故障先诊断，健康图谱的Vue回调覆盖不足用源码与测试补充。纯文档/已定位机械配置不要求图谱。生成图谱时采用index-only/skip-agents-md/skip-skills，保留人工维护入口。

## 渐进式披露约定

1. 根AGENTS：常驻边界与触发条件，目标不超过80行。不要放完整组件目录或历史执行日志。
2. 前端AGENTS/专题索引：把任务描述映射到具体规范。索引每行写清“何时读、读哪份、下一步查哪里”。
3. 主题正文：共用规则与当前实现定位放在一起。只在相关任务触发时读取。
4. 页面/业务规格、源码、测试证据：按页名、状态名、REQ等定位，不为改一个颜色全读整套PRD。

新文档须从最近的导航入口可达；优先扩充现有专题，只有出现独立阅读分支才拆新文件。数值和脚本以源码/配置为唯一执行来源，文档讲语义、限制与选择原因，避免维护第二套易失效清单。

修改规范时更新最近入口；规范改动若影响行为，关联页面与测试。历史记录保持时点，不把过去的“未选定”记录改成伪造的当时已完成。
